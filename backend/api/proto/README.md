# API-контракты

Protobuf-контракты в `online_market/v1` задают независимый от транспорта API
для клиентских приложений и административной панели. Их можно предоставлять
через gRPC, gRPC-Web, Connect или шлюз HTTP/JSON без изменения прикладного слоя.

HTTP/JSON-маршруты для отдельного gRPC-Gateway описаны во внешней конфигурации
`http/online_market_v1.yaml`. Она намеренно хранится отдельно от protobuf:
существующие gRPC-контракты не получают транспортных аннотаций, но генерация
gateway остаётся детерминированной.

Общие сведения и описания сервисов OpenAPI находятся в
`http/online_market_v1.openapi.yaml`.

Методы чтения корзины и публичного заказа используют `POST`, потому что
`cart_token` и `order_token` являются секретами и не должны попадать в URL,
историю браузера или access-логи.

## Сервисы

- `CatalogService` предоставляет товары и категории.
- `CartService` управляет анонимными серверными корзинами.
- `OrderService` оформляет заказ из корзины и позволяет покупателю получить
  созданный заказ.
- `AdminAuthService` управляет сессиями администраторов.
- `AdminCatalogService` управляет товарами и категориями. Удаление товара
  выполняется мягко: его доступность изменяется на `archived`.
- `AdminOrderService` предоставляет список заказов, позволяет изменять их и
  получать историю аудита.

## Правила контрактов

- Версии пакетов и каталогов являются частью публичного API. Для ломающих
  изменений требуется новый пакет, например `online_market.api.v2`.
- Изображения товаров не входят в MVP. Номера и имена ранее предусмотренных
  protobuf-полей зарезервированы и не должны использоваться повторно.
- Идентификаторы передаются строками UUID, если для конкретного поля явно не
  указано иное.
- `Money.minor_units` содержит целую сумму в минимальных единицах валюты. Все
  итоговые суммы рассчитывает сервер; значениям итогов от клиента доверять
  нельзя.
- Токены страниц непрозрачны и не должны разбираться клиентами.
- `expected_version` обеспечивает оптимистичную блокировку. Нулевое значение
  означает, что клиент не запрашивает проверку версии. При несовпадении
  возвращается статус `ABORTED`.
- Пути `FieldMask` задаются относительно соответствующего сообщения изменения.
  Поле можно явно очистить, передав его путь и нулевое значение.
- `CreateOrderRequest.idempotency_key` уникален для одной попытки оформления.
  Повтор с тем же содержимым возвращает исходный результат, а использование
  ключа с другим содержимым отклоняется.
- Токены корзины и публичного просмотра заказа предоставляют доступ к ресурсу.
  Их следует передавать только через TLS и никогда не записывать в журналы
  приложения.
- JSON-кодирование соответствует protobuf JSON mapping: имена полей имеют
  форму `lowerCamelCase`, enum передаются строками, а `int64` и `uint64` —
  десятичными строками. Это относится в том числе к `Money.minor_units`,
  `version` и `expected_version`.
- Все методы `AdminOrderService` и `AdminCatalogService` требуют токен доступа
  в метаданных транспорта: `authorization: Bearer <token>`. Обновление и
  завершение сессии используют токен обновления из сообщения запроса.
- Некорректные входные данные возвращаются как `INVALID_ARGUMENT`, отсутствующие
  ресурсы — как `NOT_FOUND`, недействительные или просроченные учётные данные —
  как `UNAUTHENTICATED`, недостаточные права — как `PERMISSION_DENIED`, а
  недопустимые переходы статуса заказа — как `FAILED_PRECONDITION`.

Уведомления о заказах намеренно не представлены в контрактах клиентских
приложений. Прикладной модуль заказов создаёт запись в очереди исходящих
сообщений, а внутренний Go-интерфейс позволяет реализовать доставку через
Telegram, WhatsApp или другой канал.

## Генерация серверного Go-кода

Из корня репозитория выполните `make proto-generate`. Цель генерирует
protobuf-сообщения, серверные gRPC-интерфейсы и `*.pb.gw.go` в `backend/gen`, а
объединённую OpenAPI 2.0-схему — в
`backend/gen/openapi/online_market.swagger.json`.

В `PATH` должны быть заранее доступны следующие инструменты:

- `protoc`;
- `protoc-gen-go`;
- `protoc-gen-go-grpc`;
- `protoc-gen-grpc-gateway`;
- `protoc-gen-openapiv2`.

Makefile не устанавливает и не обновляет эти инструменты автоматически.

### Генерация в Docker

Если protobuf-инструменты не установлены локально, выполните
`make proto-generate-docker`. Цель собирает изолированный образ генератора,
подключает контракты только для чтения, а `backend/gen` — как каталог вывода.
Сгенерированные файлы записываются непосредственно в репозиторий от текущих
UID и GID пользователя.

Версии плагинов генератора зафиксированы. При необходимости их можно явно
переопределить:

```shell
make proto-generate-docker \
  PROTOC_GEN_GO_VERSION=v1.36.12 \
  PROTOC_GEN_GO_GRPC_VERSION=v1.6.2 \
  PROTOC_GEN_GRPC_GATEWAY_VERSION=v2.32.0
```

Для первой сборки образа нужен доступ к реестру Docker, репозиторию пакетов
Alpine и прокси Go-модулей. Последующие сборки могут использовать кэш слоёв
Docker.
