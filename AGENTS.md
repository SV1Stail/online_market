## Назначение проекта

Этот репозиторий для онлайн магазина различных товаров.

HTTP/JSON gateway вынесен в отдельный репозиторий `online_market_gateway`.
Исходные контракты (`.proto`, HTTP mappings, OpenAPI) остаются здесь;
сгенерированный Go-код для gateway публикуется из отдельного модуля
`contracts/` с зафиксированной версией.

## Технологический стек

- Язык: backend: golang; frontend: JS, CSS, HTML
- Хранилище данных: для данных PostgreSQL, для кэша Redis
- Менеджер зависимостей: go modules
- Тестирование: unit тесты, e2e тесты на моках
- Сборка и CI: docker, docker-compose

Не заменяй выбранные технологии без явного запроса.

## Структура репозитория
- `backend/` — содержит код для backend
- `frontend/` — содержит код для frontend
- `build/` — содержит файлы для развертывания всего приложения на удаленном сервере и для локального развертывания (в целях тестирования)

### backend Golang

Код проекта должен быть разбит на packges по смыслу и выполняемым задачам
- `backend/internal/` — внутренние пакеты которые используются на беке
- `backend/migration/` — содержит данные для миграций БД (таблицы, индексы, сущности на уровне БД)
- `backend/Makefile` — содержит набор целей для локального развертывания, тестирвоания бекенда
- `backend/build` — содержит файлы для развертывания только бекенда
- `backend/Doc` — документация

При добавлении файлов соблюдай существующее разделение по слоям и модулям.

### frontend
Код проекта должен быть разбит на packges по смыслу и выполняемым задачам
- `frontend/build` — содержит файлы для развертывания только фронта
- `frontend/Makefile` — содержит набор целей для локального развертывания, тестирвоания фронта

При добавлении файлов соблюдай существующее разделение по слоям и модулям.

## Рабочий процесс

Перед внесением изменений:

1. Прочитай относящиеся к задаче файлы и тесты.
2. Проверь локальные соглашения в ближайших модулях.
3. Оцени влияние изменений на публичные интерфейсы и обратную совместимость.
4. Если требования неоднозначны и варианты существенно отличаются, задай уточняющие вопросы в виде нумерованного списка.

Во время работы:

- Вноси минимально достаточные изменения.
- Не переписывай соседний код без необходимости.
- Следуй существующей архитектуре и стилю проекта.
- Не редактируй сгенерированные файлы вручную.
- Не оставляй закомментированный код, временные заглушки и отладочный вывод.
- Существенные допущения явно указывай в итоговом сообщении.

## Архитектурные правила

### backend Golang
- для миграций исползуй go-migrate
- используй testify для unit-тестов
- используй интерфейсы для работы с зависимостями
- если функция должна возвращать более 1 аргумента не учитываю error, то нужно возвращать указатель на структуру с этими аргументами
- не скачивай зависимости самостоятельно, максимум можешь подготовить go.mod файл с названием модуля и версией языка

Новые абстракции добавляй только при наличии реального повторного использования или архитектурной необходимости.

## Стиль кода

- Следуй настройкам форматтера и линтера репозитория.
- Используй существующие соглашения по именованию.
- Предпочитай простой и читаемый код.
- Избегай скрытых побочных эффектов.
- Не дублируй логику, если в проекте уже есть подходящая реализация.
- Комментарии должны объяснять причины решения, а не пересказывать код.

## Тестирование

Не прогоняй тестирование если это не было явно указано пользователем для текущего запроса.
Не выполняй сборку проекта если это не было явно указано.

Требования:
- Проверяй не только основной сценарий, но и ошибки и граничные случаи.
- Не утверждай, что проверки прошли, если они не запускались.
- Если проверку выполнить нельзя или нужно создавать дополнительные сервисы/докер образы объясни причину и укажи, что осталось проверить.

## Зависимости

- Сначала используй возможности стандартной библиотеки и уже установленных пакетов.
- Не добавляй production-зависимости без явного обоснования.

- Не удаляй зависимость, пока не подтверждено отсутствие её использования.

## Безопасность и данные

- ломающие изменения публичного API;
- удаление или переименование публичных полей;
- необратимые миграции данных;
- изменение формата хранимых данных;
- изменение контрактов внешних интеграций.

При необходимости такого изменения опиши влияние и безопасный путь миграции.

## Правила ревью

При проверке изменений обращай особое внимание на:

- корректность и граничные случаи;
- регрессии и обратную совместимость;
- безопасность и утечки данных;
- обработку ошибок;
- конкурентный доступ и идемпотентность;
- производительность критических участков;
- достаточность тестов.

Не сообщай о чисто стилистических проблемах, которые надёжно обнаруживаются автоматическим линтером.

## Критерии готовности

Задача считается выполненной, когда:

- реализованы согласованные требования;
- сохранена обратная совместимость либо описано её изменение;
- добавлены или обновлены необходимые тесты;
- релевантные проверки успешно выполнены;
- отсутствуют временный код и отладочный вывод;
- документация обновлена (при ее наличии), если изменилось поведение;
- итоговое сообщение содержит краткое описание изменений и результаты проверок.

## Формат итогового ответа

В конце работы сообщи:

1. Что было изменено.
2. Какие файлы или компоненты затронуты.
3. Какие проверки выполнены и каков их результат.
4. Какие ограничения, риски или невыполненные проверки остались.

Пиши кратко и конкретно. Не перечисляй каждое выполненное действие, если оно не важно для проверки результата.
